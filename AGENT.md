# Где живёт агент и как он должен себя вести

Этот файл — техническое описание границы между экономикой игры (детерминированный
код, работает без AI) и AI-агентом (заменяет живых ведущих, покупателей,
поставщика и двух конкурентов). Он написан для того, чтобы на другой машине
можно было подключить другого агента/провайдера, не разбираясь заново в
остальном коде.

## Архитектура в одном абзаце

`web/game.js` (браузер) никогда не обращается к модели напрямую. Он ходит на
свой же сервер: `POST /api/agent` с телом `{task, input}`. Сервер
(`server/index.js`) передаёт это в `server/providers/index.js`, который по
переменной окружения `AGENT_PROVIDER` выбирает конкретную реализацию
(`stub.js`, `openai.js`, ...) и возвращает `{ok:true, data}` или
`{ok:false, error}`. Если сервер недоступен или вернул ошибку —
`web/game.js` сам откатывается на задокументированные детерминированные
правила (тот же фолбэк, что и в `stub.js`, продублирован на клиенте ради
устойчивости и мгновенного отклика).

```
браузер (web/game.js)
   │  fetch POST /api/agent {task, input}
   ▼
server/index.js  ──►  server/providers/index.js  ──►  server/providers/<provider>.js
                                                              │
                                                    здесь и только здесь
                                                    живут ключи и вызов модели
```

**Почему так, а не прямой вызов из браузера:** ключ провайдера не должен
попадать в код, отправляемый в браузер — иначе любой открывший страницу
может им воспользоваться от вашего имени. Это единственная причина
существования `server/`.

## Пять задач агента

Все пять задач — это ровно те пять точек, где физическая игра требует живого
человека (ведущего, покупателя, поставщика, «оппонентов»). Экономика вокруг
них (цены, склад, аренда, производство, история) полностью детерминирована и
агента не задействует.

Каждая задача описана как: `task` (строка), форма `input`, форма ожидаемого
`data` в ответе, и точный промпт, которым это решается в `openai.js` (промпты
дословно перенесены из первой версии прототипа на Claude Artifacts и уже
проверены в игре).

---

### 1. `supplier_negotiate` — поставщик решает цену при запросе опта

**Когда вызывается:** игрок жмёт «Запросить опт» на материале с тиражной
сеткой (бумага/картон).

**input:**
```json
{ "material": "Лист белой бумаги", "qty": 25, "basePrice": 10, "tierLow": 9, "tierHigh": 8 }
```
`tierLow`/`tierHigh` — `null`, если у материала нет оптовой сетки в этом эру
(не должно происходить для тиражных материалов, но провайдер должен
пережить `null` без падения).

**data (ожидаемый ответ):**
```json
{ "pricePerUnit": 9, "note": "Беру за оптовую — 20 листов и выше." }
```

**Промпт:**
```
Ты — поставщик материалов для команд в деловой игре «Снежинка». Правила твоей роли:
Сами никогда не предлагай скидку первым. Если участник команды просит скидку — в первую очередь предложи закупиться оптом по своему прайс-листу. В особых случаях можешь дать дополнительную скидку до 5%.
Твой закрытый (не показывается командам) прайс-лист на "{material}" в этом квартале: розница {basePrice} у.е./шт, опт от 20 до 50 шт — {tierLow} у.е./шт, опт от 51 шт — {tierHigh} у.е./шт.
Команда хочет купить {qty} шт. "{material}". Реши цену за штуку по своим правилам (примени опт, если объём подходит; иначе можешь дать не более 5% скидки, если объём внушительный, иначе не давай скидку).
Ответь JSON: {"pricePerUnit": число, "note": "короткая реплика поставщика игроку, по-русски, 1 фраза"}
```

**Поведенческое требование (важно для качества, не только формат):**
поставщик никогда не даёт скидку первым и не даёт больше 5% сверх
задокументированных оптовых тиров — это прямая норма из «Инструкции для
ведущего» физической игры, а не декоративная деталь промпта. Если провайдер
её игнорирует (например, слабая модель "по доброте" даёт 20% скидку) —
дебрифинг перестаёт быть сопоставим с оригинальной механикой игры.

### 2. `buyer_decision` — покупатель решает, купить ли по цене выше максимума

**Когда вызывается:** на этапе переговоров, если цена игрока в витрине выше
максимальной цены покупателя не более чем на 25%, и игрок сформулировал
обоснование (питч).

**input:**
```json
{ "buyerNum": 2, "item": "Ёлочки", "maxPrice": 165, "askPrice": 180, "pitch": "Именная надпись бесплатно" }
```

**data:**
```json
{ "accept": true, "note": "Ладно, за именную надпись — беру." }
```

**Промпт:**
```
Ты играешь роль Покупателя №{buyerNum} в деловой игре «Снежинка». Твои правила поведения:
Ты обычный покупатель, приобретаешь товары для личного пользования или в подарок. Твоя задача — удовлетворить свою потребность в товарах с наилучшим соотношением цены и качества.
Если магазин пытается продать товар по цене выше максимальной, это должно быть обосновано чем-то, что имеет для тебя значение: качество товара, персонализация (надписи/изображения по заказу), индивидуальный подход и т.д. Если цена завышена без веских оснований — ты отказываешься и ссылаешься на то, что купишь такой же товар на маркетплейсе Wildzone по рыночной цене.
Твоя максимальная цена на "{item}" в этом квартале — {maxPrice} у.е. (это твоя внутренняя информация, никогда не называй её продавцу напрямую в поле note).
Продавец предлагает тебе "{item}" за {askPrice} у.е. и говорит: "{pitch}"
Прими решение и ответь JSON: {"accept": true/false, "note": "твоя короткая устная реплика продавцу, по-русски, 1-2 фразы, не называй точную максимальную цену"}
```

**Поведенческое требование:** покупатель не должен «сливать» свою
максимальную цену в `note` — это ключевое для сохранения принципа игры
«команды не знают бюджет и список покупателя заранее». Если провайдер
регулярно проговаривает точные цифры — стоит ужесточить промпт (например,
явно запретить упоминание чисел в `note`).

### 3. `competitors` — решения двух AI-конкурентов на квартал

**Когда вызывается:** один раз в начале разрешения квартала, до подсчёта, кто
что купил.

**input:**
```json
{ "quarterLabel": "4 кв. 2026", "capacity": "1900-2800 у.е.", "skuLines": "Снежинки маленькие: рыночная цена 19 у.е.; Ёлочки: рыночная цена 165 у.е.; ..." }
```

**data:**
```json
{
  "competitors": [
    { "name": "Конкурент 1", "prices": { "Ёлочки": 160, "Шляпы бумажные": 30 }, "rentChairs": 2 },
    { "name": "Конкурент 2", "prices": { "Ёлочки": 175, "Кораблики": 52 }, "rentChairs": 1 }
  ]
}
```
Ровно два элемента в `competitors`, иначе клиент откатится на фолбэк.

**Промпт:**
```
Ты моделируешь решения ДВУХ конкурирующих команд в деловой игре «Снежинка» на квартал {quarterLabel}. Каждая команда — производственно-торговая компания, продаёт снежинки/ёлочки/шляпы/кораблики/самолёты, конкурирует за тех же покупателей. Ориентировочная ёмкость рынка в этом квартале: {capacity} у.е. Рыночные цены-ориентиры: {skuLines}.
Для каждой из двух команд реши: какие 2-4 товара она выставит на витрину и по какой цене (обычно около рыночной цены, немного выше или ниже — по своей стратегии), и сколько стульев (0-3) она арендует в одном торговом центре.
Ответь JSON: {"competitors":[{"name":"Конкурент 1","prices":{"товар":цена,...},"rentChairs":число},{"name":"Конкурент 2","prices":{...},"rentChairs":число}]}
```

### 4. `debrief_facts` — нейтральная хроника квартала для дебрифинга (шаг 2 из 4)

**Когда вызывается:** при открытии второго шага дебрифинга, один раз за
сессию дебрифинга (результат кэшируется в `S.debrief.facts`).

**input:**
```json
{ "log": "## 1 кв. 2026\nЗакупки: ...\nАренда: ...\n..." }
```
`log` — текст, собранный функцией `logSummaryText()` в `web/game.js` из
`S.decisionLog` (по одному блоку на квартал: закупки, аренда, производство,
цены, переговоры, финансовый результат, пояснение игрока).

**data:**
```json
{ "text": "1 кв. 2026: закуплено 3 позиции материалов...\n2 кв. 2026: ..." }
```

**Промпт:**
```
Ты помогаешь провести дебрифинг после деловой игры «Снежинка» (бизнес-симуляция для руководителей). Ниже — фактический лог решений одного участника по кварталам. Составь нейтральное, короткое фактологическое изложение того, что происходило — только события, без оценок, советов и подбадриваний. Пиши по-русски, по кварталам, пунктами.

{log}
```

**Почему это отдельный, обязательно нейтральный шаг:** методика дебрифинга
(«эмоции → факты → анализ → выводы») требует, чтобы участник сначала увидел
голые факты без интерпретации, и только потом — анализ. Если провайдер
подмешивает оценки на этом шаге («вы допустили ошибку»), это ломает саму
методику, а не просто портит стиль текста.

---

### 5. `debrief_analysis` — поведенческий анализ (шаг 3 из 4)

**Когда вызывается:** при открытии третьего шага дебрифинга, один раз за
сессию (кэшируется в `S.debrief.analysis`), после того как шаг фактов
пройден и игрок мог дописать факты от себя.

**input:**
```json
{ "log": "## 1 кв. 2026\n...", "addedFacts": "Забыл упомянуть: подняли цену на ёлочки специально" }
```
`addedFacts` может быть пустой строкой.

**data:**
```json
{ "text": "Риск и планирование: ...\nПереговорная позиция: ...\nАдаптивность: ..." }
```

**Промпт:**
```
Ты — HR-фасилитатор дебрифинга деловой игры «Снежинка» для топ-менеджеров ДНС. На основе лога решений участника ниже сформулируй наблюдения о его проявлениях в трёх зонах: (1) отношение к риску и планированию, (2) переговорная позиция и работа с возражениями/отказами, (3) адаптивность при изменении рыночных условий (например, ввод нового SKU «Дед Мороз» в 4 квартале). Для каждой зоны — 2-3 предложения, с опорой на то, что конкретно произошло в игре, без общих фраз и без оценки «хорошо/плохо» — фиксируй наблюдаемое поведение и на что стоит обратить внимание в реальной работе. Пиши по-русски.

Лог решений:
{log}

{Дополнение участника к фактам: addedFacts}
```

**Это самая важная задача из пяти.** Как явно указал заказчик прототипа:
результат игры (кто заработал больше) — не главный результат; главный
результат — то, что этот шаг формулирует про проявления руководителя. Если
меняете провайдера и получаете более слабую модель, в первую очередь
проверяйте качество именно этого ответа, а не супplier/buyer-механику.

## Как подключить другого провайдера

1. Создайте `server/providers/<name>.js` с единственной обязательной
   функцией `async function run(task, input)`, которая по `task`
   диспетчеризует на 5 задач выше и возвращает `data` в описанной форме
   (или бросает исключение — сервер сам превратит его в `{ok:false}`, а
   клиент откатится на фолбэк).
2. Скопируйте промпты из этого файла (или из `openai.js`) дословно — это
   уже проверенные в игре формулировки, менять их стоит осознанно и с
   повторным тестированием, а не «на глаз».
3. Зарегистрируйте провайдер в `server/providers/index.js`
   (`const <name> = require('./<name>')` + добавить в объект `providers`).
4. В `.env` выставьте `AGENT_PROVIDER=<name>` и нужные этому провайдеру
   переменные.
5. Готовые заготовки с описанием, что именно доделать, лежат в
   `server/providers/gigachat.js` и `server/providers/yandexgpt.js` — это
   два кандидата, между которыми пользователь ещё не выбрал (см. README).

## Что должен обеспечивать любой провайдер, независимо от реализации

- Не падать без объяснимой причины: если модель недоступна — лучше бросить
  понятную ошибку (сервер её залогирует, клиент откатится на фолбэк), чем
  вернуть мусор, который сломает JSON.parse на клиенте.
- Отвечать в пределах разумного времени (несколько секунд на задачу) —
  игрок ждёт синхронно на большинстве задач.
- Для JSON-задач (`supplier_negotiate`, `buyer_decision`, `competitors`) —
  возвращать валидный JSON без markdown-обёртки (без ```json ... ```).
- Не педалировать реальные бренды/имена людей в ответах — это симуляция
  вымышленных ролей.
